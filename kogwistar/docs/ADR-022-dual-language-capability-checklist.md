# ADR-022 Dual-Language Capability Checklist

**Updated:** 2026-10-26
**Status vocabulary:** `NOT STARTED`, `IN PROGRESS`, `PASS`, `FAIL`, `BLOCKED`.
`PASS` requires a named test, benchmark, or inspected code path. A design
decision by itself does not prove an implementation gate. Update this file as
each capability is implemented; record its implementation, backend, interpreter,
and CI evidence rather than assigning one percentage to the whole port.

## Latest verification update (2026-10-25)

- The shared `kogwistar-store` contract now owns the canonical projection
  mapping for node, edge, document, and domain, plus a separate node/edge-only
  lifecycle validator. PostgreSQL delegates to these functions rather than
  carrying duplicate kind/table mappings. Rust unit suites pass **24** shared
  store tests and **11** PostgreSQL store tests, including exact kind/table
  mapping and lifecycle rejection of document/domain targets.
- Live Windows CPython 3.13 PostgreSQL regression:
  `tests/core/test_rust_postgres_transaction_session.py` plus
  `tests/core/test_edge_metadata_serialization.py`: **34 passed, 0 failed**.
  This includes document/domain atomic add, document rollback delete, and
  node/edge tombstone-before-purge behavior. The rollback test now performs its
  canonical tombstone and physical purge within the same transaction before
  asserting that rollback restores the row and event history. The rebuilt
  PyO3 extension was used for this run, proving the shared validator through
  the Python-to-Rust call path.
- DL-06E remains **IN PROGRESS**: these PostgreSQL cases establish only the
  verified slice; broader backend, async, failure-injection, and full-stack
  cross-language atomicity requirements remain open.
- Graph projection reads now have a source-compatible optional keyset-page API.
  PostgreSQL uses the same explicit C-collation order for cursor comparison and
  page ordering; the in-memory store preserves legacy insertion order for
  ordinary reads and sorts only paged reads. A shared collector rejects
  unordered, oversized, or non-advancing pages. Evidence: memory pagination
  test in `kogwistar-store-memory`, bridge optional-field test in
  `kogwistar-python`, and the live PostgreSQL projection and conversation-route
  tests, all passing on Windows CPython/Rust. This removes the conversation
  route's silent 10,000-record truncation; the collector still retains all
  records in memory, so bounded-memory scaling remains open. The Python facade
  regression `test_postgres_meta_facade_forwards_optional_graph_projection_cursor`
  confirms that `after_id` crosses the facade unchanged and omission preserves
  the old operation shape; the entire facade module passed **11 tests** on
  elevated Windows CPython 3.13. A new live Python facade → compiled Rust bridge
  → PostgreSQL page-boundary test is present, but its local run skipped because
  Docker's named pipe was unavailable; keep live execution open until Docker-
  enabled CI or a local PostgreSQL fixture passes it.
- The shared typed graph-mutation validator now also invokes the base mutation
  contract before accepting a typed envelope, preventing typed callers from
  bypassing namespace, operation, table, payload-shape, or vector checks.
  `typed_graph_mutation_cannot_bypass_base_mutation_validation` covers these
  rejection cases. Elevated Windows CPython 3.13 workspace verification passed
  **247 Rust tests with 1 intentionally ignored**; this does not close the
  remaining PyPy, other CPython, hosted-CI, or backend/live-DSN matrix.
- Node/edge graph mutations now require the event payload's canonical `id` to
  equal the projection record ID in both the shared Rust effect-owner validator
  and Python's versioned wire validator. This prevents an event for one entity
  from materializing under another entity's projection key. Evidence:
  `cargo test --manifest-path rust/Cargo.toml -p kogwistar-store --lib` (**26
  passed**) and `poetry run pytest tests/core/test_graph_mutation_contract.py -q
  -p no:cacheprovider` (**13 passed**) on Windows CPython 3.13. This is a
  graph-mutation identity invariant, not a claim of broad stack parity.
- Post-change Windows Rust workspace verification with loopback access passed
  **248 tests, 0 failed, 1 intentionally ignored** across all library crates;
  the API crate independently passed **69/69**, including the local OIDC and
  real-TCP tests that failed or stalled in the restricted run. The restricted
  run was interrupted after confirming its loopback-dependent stall; it is not
  counted as a product failure or as passing evidence.
- Strict Rust persistent node/edge decoding now matches Python's shared
  `TombstoneMixin` and `LevelAwareMixin` behavior: omitted lifecycle defaults
  are materialized, legacy `deleted` becomes `tombstoned`, metadata-only levels
  populate the typed field, explicit field levels overwrite metadata, and
  Python-accepted negative integer levels remain accepted. Decode preserves the
  distinction between an omitted level field and explicit `null`, matching
  Python even when metadata contains a level; Python-compatible coercions for
  integer strings, booleans, and integral floats are also covered, while
  fractional values fail validation. The original envelope payload remains
  unchanged for lossless forwarding. Evidence:
  `graph_model::tests::persistent_node_and_edge_normalize_python_mixin_fields`,
  the strict persistent model lifecycle tests (**65 Rust contract tests pass**),
  and `test_edge_model_shares_tombstone_and_level_metadata_contract` (Python).
- After these model-contract changes, the loopback-enabled Windows Rust
  workspace suite passed **249 tests, 0 failed, 1 intentionally ignored**;
  this includes 69 API tests and all storage/runtime/bridge crate tests. The
  focused Python edge mixin contract also passed on CPython 3.13.

## Completion rule

The dual-language architecture is implemented for a capability only when its
applicable contract, transaction-seam, authority, parity, and support-matrix
gates pass. A native
end-to-end performance claim additionally requires DL-12 or DL-13 as applicable
and DL-19/20 for the stated workload. Open items remain open even if a narrow
benchmark or one deployment's canary passes.
