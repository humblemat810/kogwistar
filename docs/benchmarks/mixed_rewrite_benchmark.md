# Mixed Workload Rewrite Benchmark

> **Graph-scope correction (2026-10-22):** the earlier v1/v2 storage and MCP
> measurements used generic entity-event/projection rows and did not persist a
> relationship edge per write. They remain useful as substrate-level baselines,
> but they are **not** evidence for a graph-operation Rust rewrite. The v3
> contract below adds valid Kogwistar Node+Edge bundles, immutable source spans,
> explicit endpoints, and validates both graph entities on every read. Only v3
> graph-bundle results may be used for the rewrite decision.

## Purpose

This benchmark builds reproducible evidence for or against a broader Kogwistar
Rust rewrite. It is not a Python-versus-Rust language microbenchmark: results
include each public facade, its transaction/session lifecycle, JSON conversion,
and the underlying store behavior.

## Current Runnable Slice

The SQLite runner is `scripts/rust_port_persistent_benchmark.py`. It compares
Python `EngineSQLite`, Rust per-call, Rust cached-session, and a standalone
Rust `SqliteStore` process. Existing isolated event/projection workloads remain
available. Versioned sequential read-after-write operations are generated by
`scripts/mixed_workload.py` and saved to the output directory as
`read_after_write_trace.v1.json`. The filename is retained for artifact
compatibility, while the payload schema is
`kogwistar-mixed-rewrite-trace/v2`; the Rust native consumer accepts both v1
and v2. All four modes consume the same trace and final-state digest.

Each v3 logical write appends a valid Node event and a linked Edge event, then
replaces both named projections in one transaction. Reads validate both
entities, edge endpoints, and exact source-span excerpts before moving on. The
benchmark verifies read-your-writes and compares canonical final-state digests.
Database footprint includes SQLite main, WAL, and shared-memory files.
Python host CPU/RSS and native Rust child CPU/sampled peak RSS are recorded for
the benchmark paths that expose those process boundaries.

Sequential MCP samples also include `seam_metrics`: observed tool dispatches,
Rust-facade FFI calls, serialized payload bytes, transaction-boundary calls, and
HTTP transport requests. Python-host counters are scoped to that process; the
benchmark-only Rust-native server exposes the same counters through its private
`/metrics` endpoint, with `ffi_calls: 0` asserted by the native implementation.
Process CPU/RSS measurements remain separate from these logical counters.

The native counter path was verified with a two-sample, one-item sequential
smoke on 2026-10-25 using `run_benchmark(..., modes=("rust_native",),
include_concurrent=False)`. Its three-operation sample reported
`tool_dispatches=3`, `transport_requests=3`, `transaction_boundaries=1`,
`serialized_bytes=2667`, and `ffi_calls=0`. The probe required an elevated
Windows loopback permission; the restricted sandbox's `WinError 10013` is not
application evidence.

The same endpoint was verified under the one-writer/four-reader concurrent
balanced trace on 2026-10-25: 5 operations completed with
`tool_dispatches=5`, `transport_requests=5`, `transaction_boundaries=1`,
`serialized_bytes=3023`, and `ffi_calls=0`.

Concurrent profiles are implemented in `scripts/mixed_concurrent_benchmark.py`
for SQLite events/projections, Chroma with SQLite metadata, and PostgreSQL/
pgvector with SQLite metadata. Each write has an individual commit boundary.
Readers inspect the prior committed head while a write is still uncommitted,
then the newly committed head. The v3 trace declares the exact revision each
read must observe. Balanced runs four graph reads per write; read-heavy runs
eight. Startup is reported separately, and Python and Rust-backed SQLite state
digests are compared. Vector upserts happen before the SQLite authoritative
event/projection commit, so a failed graph commit can leave an orphan vector;
this benchmark verifies retrieval parity, not atomic cross-store transactions.

The contention probe uncovered a Python/Rust bridge issue: blocking Rust SQLite
operations held the CPython GIL, preventing readers and writers from making
progress together. `store_sqlite_json` now keeps Python ownership entry/exit
under the GIL but detaches the pure-Rust store call. The first concurrent
benchmark attempt also exposed per-read connection/schema initialization and a
registry bug that confused a reusable native connection session with an active
transaction. Fresh native opens reran schema DDL, causing a reader opened during
an uncommitted write to request schema locks and wait for that write to commit.
Rust SQLite now uses `PRAGMA user_version` as a migration marker: legacy or
unversioned databases still run the additive initializer/migrations once, while
routine opens of a current schema skip DDL. `RustEngineSQLite.session()` scopes
reusable Rust connections, and the ownership registry tracks active
transactions separately. The benchmark runs blocking concurrent MCP handlers
in worker threads and keeps the pure-Rust bridge call detached from the GIL.
Together these changes allow exact pre-commit visibility without serializing the
trace.

The Python-compatible `execute_batch()` facade on the Rust SQLite and
PostgreSQL meta-store surfaces is an additive optimization for callers that
explicitly need one atomic native transaction. It reduces repeated
Python/Rust crossings for that group, while preserving the existing
single-operation methods. The shared `transaction_active` guard rejects nested
batches rather than letting backend-specific transaction behavior leak through
the compatibility seam. The benchmark's sequential read-after-write trace
deliberately keeps each write at its own commit boundary, so batching is not
used to hide visibility or acknowledgement semantics. A batch result is
therefore not evidence that the full mixed workload has become native.

Graph mutation groups follow the same rule at the Rust trait boundary. The
shared `GraphMutationStore::apply_graph_mutations_atomic()` capability fails
closed unless a backend explicitly provides one transaction for the complete
group. PostgreSQL provides that implementation through its native unit of
work; the in-memory and current Rust SQLite stores intentionally reject the
capability rather than silently degrading to per-mutation commits. This is a
correctness boundary, not a claim that the whole graph workload is native.

The backend harness is `scripts/mixed_backend_benchmark.py`. It compares three
distinct configurations without mislabeling Chroma's own SQLite metadata as a
separate graph backend: (1) SQLite events/projections only, (2) Chroma vectors
with Chroma SQLite metadata plus Kogwistar events/projections in SQLite, and
(3) PostgreSQL/pgvector vectors plus Kogwistar events/projections in SQLite.
Normalized 384-dimensional vectors are deterministically precomputed before
timing; embedding inference is excluded. Every record is upserted and every
authoritative event/projection read is checked. Vector top-1 checks use an
evenly spaced deterministic sample of at most 100 query indexes (including the
first and final record) to avoid introducing quadratic repeated-query work as
the fixture grows; pass `--vector-query-samples` to select a different bound.
Each requested vector backend performs cosine queries at those indexes,
verifies self top-1, and PostgreSQL additionally
closes/reopens the backend before re-querying. A requested but unavailable
backend fails the run.

The MCP harness is `scripts/mixed_mcp_benchmark.py`. It sends the same v3
graph read-after-write trace through the Python in-process registry, the
Python Streamable HTTP MCP endpoint, and a benchmark-only Rust/Axum JSON-RPC
`tools/call` endpoint backed by `SqliteStore`. It also runs the same Python
registry with `RustEngineSQLite` authority, so Python service overhead with
Python versus Rust persistence is separately observable. The Rust endpoint
implements the same deterministic operations and JSON-RPC tool-call response
contract, but is not a complete Streamable HTTP MCP session implementation and
is not the production Kogwistar MCP server. Concurrent MCP runs cover one
writer/four readers in Python in-process and Streamable HTTP modes with both
Python and Rust authorities, plus the Rust-native local HTTP JSON-RPC endpoint.
They validate exact pre/post-commit visibility and report throughput, operation
p50/p95/p99 latency, startup, host or native child CPU/RSS metrics, and SQLite
database/WAL footprint. All implemented paths must produce the same canonical
state digest.

Benchmark fixture construction enters the explicit `backend` model-slicing mode
while creating Node/Edge payloads. This keeps repeated stack-based mode
inference out of setup and separates Pydantic model-construction overhead from
service measurements. A Windows CPython 3.13 smoke on 2026-10-25 measured the
root plus eight graph payloads at approximately 167 ms after this change; this
is setup evidence, not service throughput. The same smoke reached the
in-process warm-up but stalled in the existing local HTTP regression before
producing a parity report. Sequential in-process modes now use a synchronous
registry dispatcher and therefore do not require a Windows event loop; a
  two-item in-process trace completed in 0.392 seconds with a deterministic
  digest. A follow-up synchronous dispatcher check on 2026-10-25 ran the same
  six-operation trace through both Python in-process and Rust-authority modes;
  both produced state digest
  `8984a097312f1d8b063c42812fa01019e3dc9ff2f7093cc51fc56b4b03ac4ce4`.
  The measured elapsed times were 188 ms and 335 ms respectively. This is
  bounded local parity evidence, not a whole-stack performance claim. It also
  does not replace the all-surface benchmark; the local HTTP shutdown/progress
  issue remains an open transport-test item.

Run a tiny all-surface MCP parity smoke (the first invocation builds the Rust
example in release mode):

```powershell

  --output .tmp/mcp-smoke `
  --items 8 --samples 2
```

`--mode both` compares Python and Rust-backed SQLite authority. Chroma and
PostgreSQL vector configurations exercise the Python service against the same
concurrent trace. The graph trace and report schemas are v3; each invocation creates
a unique sample directory. Reports include graph and vector operation latency,
graph/storage throughput, CPU time, process RSS, SQLite footprint, vector-store
footprint when measurable, warm-up, and sample variation. PostgreSQL uses and
drops a benchmark-unique schema after its size measurement.

Each backend sample uses a fresh SQLite app database, a fresh Chroma directory,
and a unique PostgreSQL schema. One warm-up is reported separately. The
fixture sizes and sample minimum are in the versioned workload contract; do
not reuse output directories for another run.

## Fixed-Resource Runtime And Authority Matrix

The runtime expansion is implemented by `scripts/run_mixed_runtime_matrix.ps1`
and `scripts/runtime_matrix/Dockerfile`. The original four isolated images run
the same Python-authority SQLite graph trace: CPython 3.14.9 with the GIL,
CPython 3.15.1 with the GIL, CPython 3.15.1 built with `--disable-gil`, and
PyPy 3.11. CPython 3.14.9 and both CPython 3.15.1 builds use checksum-verified
Python.org source archives; the two 3.15 builds differ only in the GIL build
option. Each container is limited to 4
CPU cores and 8 GiB RAM with swap disabled. Images are built before timing; a
minimal Kogwistar package and benchmark-script staging directory is copied
into each image (not the full repository), avoiding source imports over a
Windows-to-container bind mount; only result directories are bind-mounted.
The runner records interpreter/platform metadata, cgroup limits, installed
package versions, image IDs, and a digest of the exact staged source. The host
manifest also reports dependency-version differences; if versions vary across
runtime images, interpret timing as runtime-plus-dependency-stack evidence, not
a pure interpreter comparison.

The Python-authority no-GIL case is accepted only if `sys._is_gil_enabled()`
reports `False` before and after the Kogwistar benchmark path. An extension
that silently re-enables the GIL makes a runtime result invalid instead of
being reported as a free-threaded measurement. The additional Rust-authority
configuration builds the existing PyO3 SQLite extension for CPython 3.15.1t,
then runs only the Rust storage-authority mode on the same SQLite trace. Its
report captures GIL state immediately after native-extension import and after
the workload; both must remain disabled for acceptance. This is a
compatibility/performance probe, not a claim that the extension is already
free-threading safe. The compiled extension is copied into a final image based
on the unchanged no-GIL runtime image, so the Rust toolchain/compiler used to
build it is not present in the measured container. CPython/PyPy version
identity and actual cgroup CPU/memory limits are also checked at runtime. The
limit probe supports both cgroup v2 and v1; the local Docker Desktop engine
exposes v1 quota files (`400000/100000`) and an 8 GiB memory limit. The
project is imported from the checked-out source via
`PYTHONPATH`; this specifically compares runtime execution and does not claim
that current package metadata accepts CPython 3.15 or PyPy 3.11 through pip.

mount; only compact JSON reports and deterministic traces are exported after
